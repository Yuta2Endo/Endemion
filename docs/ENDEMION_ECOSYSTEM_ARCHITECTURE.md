# Архитектура Endemion ID

## Схема

```
                 auth.endemion.online — Endemion ID (OpenID Connect провайдер)
                 auth/ в этом репозитории, своя база data/auth/auth.sqlite
                    │  вход, регистрация, почта, пароль, аватар, сессии
          ┌─────────┴──────────┐
   Authorization Code + PKCE   Authorization Code + PKCE
          │                    │
   endemion.online        life.endemion.online
   своя сессия            своя сессия (el_session)
   (endemion_session)     игрок ── жизни, сохранения
   пользователь ── полка,
   рецензии, подписки
```

- **Endemion ID** хранит аккаунт: `sub` (UUID, не меняется), почту, username, отображаемое имя, аватар, хеш пароля, статус. Только он проверяет пароль.
- **Сайты** хранят свои данные как раньше. Пользователь сайта связан с аккаунтом через `users.endemion_sub`, игрок Life — через `players.endemion_sub`. Почта и username для связи данных не используются: их можно менять.

## Почему так

| Вариант | Почему не выбран |
|---|---|
| Общая база двух сайтов | SQLite и PostgreSQL, `INTEGER` и `UUID`, разные хеши паролей: пришлось бы переписать оба проекта |
| Общий cookie на `.endemion.online` | Запрещено заданием; утечка cookie одного сайта давала бы вход на другой |
| Keycloak | Около 1 ГБ памяти, а на сервере 2 ГБ на всё; отдельный стек (Java) |
| Свой протокол | Запрещено заданием; ошибки в таком коде — частая причина взломов |
| **oidc-provider 9.13** | Сертифицированная реализация OpenID Connect (panva), MIT, Node.js как у обоих сайтов, в проверке занял ~39 МБ |

Сайты используют `openid-client` 6.8 того же автора: он проверяет подпись ID token, `iss`, `aud`, `exp`, `nonce`, `state` и PKCE.

## Вход

1. Пользователь нажимает «Войти» на endemion.online. `GET /auth/login` создаёт `state`, `nonce` и `code_verifier`. Verifier и nonce остаются в базе сайта (`oidc_logins`), в браузер уходит только `state` в cookie `endemion_oidc` (`HttpOnly`, путь `/auth/callback`, 10 минут).
2. Браузер уходит на `auth.endemion.online/auth?…&code_challenge=…&code_challenge_method=S256`. Endemion ID показывает форму входа или регистрации.
3. После входа Endemion ID возвращает браузер на `https://endemion.online/auth/callback?code=…&state=…`. В адресе только одноразовый код, живущий 60 секунд; без verifier и секрета клиента он бесполезен.
4. Сервер сайта меняет код на токены (`POST /token` с секретом клиента), проверяет ID token, находит или создаёт пользователя и создаёт свою сессию. Refresh token хранится в сессии, зашифрованный AES-GCM.
5. Пользователь открывает life.endemion.online и нажимает «Войти через Endemion ID». Шаги 1–4 повторяются, но на шаге 2 у Endemion ID уже есть сессия: формы нет, браузер сразу возвращается с кодом.

Токены не передаются через адрес и не попадают в браузер: обмен кода идёт между серверами.

## Связь с Endemion ID после входа

Раз в 5 минут сессия сайта обменивает refresh token на новый (каждый токен одноразовый). Так сайт узнаёт:

- о выходе, отзыве сессии или блокировке в Endemion ID — провайдер отказывает, сайт удаляет свою сессию;
- о новом имени, username, почте или аватаре — они приходят в ID token и сохраняются у сайта.

Если Endemion ID недоступен, сессия работает до часа после последней удачной сверки, потом нужен новый вход.

Refresh token выдаётся без `offline_access`: он живёт не дольше центральной сессии Endemion ID (30 дней) и пропадает при выходе там.

## Связь со старыми аккаунтами

Порядок поиска пользователя сайта по ответу Endemion ID (`functions/_lib/endemionId.js`, `resolveUser`):

1. уже связан по `sub`;
2. перенесённый скриптом пользователь: Endemion ID передаёт сайту номер старого пользователя в claim `https://endemion.online/legacy_user_id`;
3. пользователь сайта с той же почтой — только если Endemion ID подтвердил почту;
4. иначе новый пользователь.

В Life (`AuthService.signInWithEndemionId`): связан по `sub` → аккаунт Life с той же подтверждённой почтой → гость этого браузера → новый игрок. Если вход привёл к уже существующему игроку, жизни гостя этого браузера переходят к нему тем же кодом, что при обычном входе. По username ничего не связывается.

## Выход

- Кнопка «Выйти» на сайте удаляет его сессию и уводит на `auth.endemion.online/session/end`. Там пользователь выбирает «Выйти со всех сайтов Endemion» или только с этого сайта. Форма защищена токеном `xsrf` провайдера.
- Выход со всех сайтов отзывает refresh token'ы обоих сайтов. Второй сайт узнаёт об этом при ближайшей сверке, не позже чем через 5 минут.
- На странице `/sessions` Endemion ID можно завершить другие устройства: их токены отзываются так же.

## Профиль

Страница `auth.endemion.online/account`: Endemion ID (`sub`), username, отображаемое имя, почта и статус её подтверждения, дата регистрации, аватар, смена почты и пароля. Страница `/sessions`: активные сессии с устройством, адресом и сайтами, завершение одной или всех остальных.

На endemion.online имя, адрес профиля, аватар и пароль для аккаунтов Endemion ID меняются только в Endemion ID (поля скрыты, API отвечает 409). Описание, цвет, жанры и приватность остаются на сайте. В Life показываются имя, `@username`, аватар и номер Endemion ID.

## Модель данных Endemion ID

| Таблица | Что хранит |
|---|---|
| `accounts` | `sub` (UUID, первичный ключ), `email` (уникальный, без учёта регистра), `email_verified_at`, `username` (уникальный, без учёта регистра), `display_name`, `avatar_version`, `password_hash` (scrypt или перенесённый pbkdf2), `status` (active/blocked), `failed_logins`, `locked_until`, даты |
| `platform_links` | Перенесённые аккаунты: `sub` ↔ номер пользователя на сайте. Уникально по сайту и номеру |
| `auth_tokens` | SHA-256 ссылок подтверждения почты (24 часа) и восстановления пароля (1 час), почта, на которую ушло письмо |
| `oidc_models` | Хранилище oidc-provider: сессии, interaction, коды, токены, гранты |
| `rate_events` | Счётчики попыток для лимитов |
| `audit_log` | События безопасности: входы, неудачи, смена пароля, почты, профиля, отзыв сессий |
| `import_conflicts` | Пользователи сайта, которых перенос не смог безопасно перенести |

Изменения у сайтов (только добавления, старые данные не меняются):

- сайт, миграция `0017_endemion_id.sql`: `users.endemion_sub` (уникальный), `user_profiles.avatar_url`, в `sessions` — `refresh_token`, `refreshed_at`, `last_ok_at`, `auth_time`, таблица `oidc_logins`;
- Life, миграция `20261103120000_endemion_id`: `players.endemion_sub` (уникальный) и поля профиля `id_*`, в `sessions` — `refresh_token`, `refreshed_at`, `last_ok_at`, таблица `oidc_logins`.

У игрока Life может быть несколько жизней, и все они принадлежат игроку, связанному с одним `sub`. Отдельная таблица игровых профилей не добавлена: сейчас её нечем наполнить, а связь «игрок ↔ sub» позволяет добавить её позже без переноса данных.

## Подключение нового сервиса

1. Добавить клиента в `OIDC_CLIENTS` Endemion ID: свой `client_id`, секрет, точные `redirect_uris` и `post_logout_redirect_uris`. Поле `platform` сейчас принимает `endemion` и `endemion_life`; для нового сервиса его нужно добавить в `auth/src/config.mjs` и в CHECK таблицы `platform_links`.
2. В сервисе: Authorization Code + PKCE S256 через `openid-client` (или любую сертифицированную библиотеку), своя сессия, связь по `sub`, сверка через refresh token.
