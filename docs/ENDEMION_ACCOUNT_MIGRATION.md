# Перенос аккаунтов в Endemion ID

## 1. Что переносится и как

| Откуда | Как попадает в Endemion ID | Пароль |
|---|---|---|
| Пользователи endemion.online | Скрипт `auth/scripts/import-endemion-users.mjs` | Хеш PBKDF2 переносится как есть. При первом входе Endemion ID проверяет его и сразу заменяет на scrypt. Сбрасывать пароль не нужно |
| Аккаунты Endemion Life | Не переносятся скриптом. Человек регистрируется в Endemion ID с той же почтой и подтверждает её; при входе в Life его аккаунт связывается сам | Старый пароль Life больше не нужен |
| Гости Life | Ничего не нужно: при входе через Endemion ID гость сам становится игроком этого аккаунта, жизни остаются | — |

Что не меняется ни в одной базе: id пользователей сайта, id игроков Life, полки, комментарии, подписки, жизни, сохранения. Миграции сайтов только добавляют столбцы и таблицы. Старые таблицы `sessions`, `password_resets` и хеши паролей сайта не удаляются: на них работает откат.

## 2. Сколько пользователей сейчас

Команды только считают строки и ничего не меняют:

```bash
ssh -i ~/.ssh/endemion_vps root@185.175.156.196 \
  "cd /opt/endemion && docker compose exec -T app node -e \"const {DatabaseSync}=require('node:sqlite');const d=new DatabaseSync('/app/data/endemion.sqlite',{readOnly:true});console.log(d.prepare('select count(*) n from users').get())\""

ssh -i ~/.ssh/endemion_vps root@185.175.156.196 \
  "cd /opt/endemion-life && docker compose -f infrastructure/docker-compose.prod.yml -f infrastructure/docker-compose.behind-proxy.yml --env-file .env exec -T postgres sh -c 'psql -U \"\$POSTGRES_USER\" -d \"\$POSTGRES_DB\" -tAc \"select (select count(*) from accounts), (select count(*) from players)\"'"
```

## 3. Конфликты

| Случай | Что делает скрипт |
|---|---|
| Почта пользователя сайта уже занята аккаунтом Endemion ID | Не переносит и не объединяет. Запись `email_taken` в `import_conflicts` и в `data/auth/import-conflicts.json`. Скрипт завершается с кодом 2 |
| Username сайта уже занят в Endemion ID | Переносит с именем `<имя>_<id>`, запись `username_renamed:...` в `import_conflicts` |
| Username сайта не подходит под правила | Переносит как `user<id>` |
| Пользователь заблокирован на сайте | Переносит со статусом `blocked`: войти он не сможет |
| Уже перенесён (есть запись в `platform_links`) | Пропускает. Скрипт можно запускать повторно |
| Аватар загружен на сайт, но файла нет на диске (картинки в S3) | Переносит без аватара, в отчёте «без файла аватара» |

Конфликт почты разбирается вручную. Если владелец аккаунта Endemion ID и пользователь сайта — один человек, ему достаточно подтвердить почту в Endemion ID: при входе на сайт его старый аккаунт свяжется по подтверждённой почте. Если это разные люди, аккаунт сайта остаётся как есть.

Связь по подтверждённой почте — это то же доверие, что у восстановления пароля по письму: кто владеет почтой, тот владеет аккаунтом. По username сайты ничего не связывают.

## 4. Порядок переноса в рабочей среде

Сначала на копии, потом на рабочих данных.

1. **Копии.** Сайт: `docker compose exec -T app node server/backup.mjs` (копия уходит и в S3, если он настроен). Life: копия базы по `docs/DATABASE_BACKUPS.md` Life. Endemion ID делает свою копию перед записью сам.
2. **Пробный запуск на копии базы сайта.** Скрипт открывает базу только на чтение, но запускать его на копии проще и безопаснее:
   ```bash
   cd /opt/endemion
   cp "$(ls -t data/backups/endemion-*.sqlite | head -1)" data/auth/site-import.sqlite
   docker compose run --rm -v ./data/files:/site-files:ro auth \
     node scripts/import-endemion-users.mjs --source /app/data/site-import.sqlite --files /site-files --dry-run
   ```
   Отчёт покажет, сколько будет перенесено, конфликтов и аватаров. В базу ничего не записывается.
3. **Перенос.** Та же команда без `--dry-run`. Перед записью скрипт делает копию `data/auth/backups/auth-before-import-*.sqlite`. Всё пишется одной транзакцией: при ошибке база Endemion ID остаётся как была.
4. **Удалить копию базы сайта:** `rm data/auth/site-import.sqlite` (в ней почты и хеши паролей).
5. **Разобрать конфликты** из `data/auth/import-conflicts.json`.
6. Включить вход через Endemion ID на сайте, потом в Life (`ENDEMION_DEPLOYMENT.md`).

Пользователи, которые зарегистрируются на сайте между копией и включением Endemion ID, в перенос не попадут. Повторный запуск скрипта на свежей копии их добавит. Проще всего запустить его ещё раз сразу перед включением `ENDEMION_ID=1`.

## 5. Staging

Отдельного staging-сервера нет. Пробный запуск (шаг 2) работает на копии рабочих данных и ничего не пишет. Полный путь входа проверен автотестами на временных базах: перенос строит базу сайта его же миграциями и хеширует пароль его же кодом (`auth/tests/import.test.mjs`). Если нужен staging с настоящими доменами, его готовит владелец (поддомены, DNS, отдельные секреты).

## 6. Откат

| Шаг | Как откатить |
|---|---|
| Вход через Endemion ID на сайте | `ENDEMION_ID=` в `.env`, `docker compose up -d app`. Старый вход паролем работает снова: пароли и таблицы не трогались. Сессии, созданные через Endemion ID, перестанут сверяться и доживут свой срок |
| Вход через Endemion ID в Life | `ENDEMION_ID=false`, перезапуск `api` |
| Перенос пользователей | Остановить auth, вернуть `data/auth/auth.sqlite` из `data/auth/backups/auth-before-import-*.sqlite` (файлы `-wal` и `-shm` удалить), запустить |
| Миграция 0017 сайта или миграция Life | Не нужен: столбцы и таблица ничему не мешают при выключенном Endemion ID. Полный откат — восстановление копии базы из шага 1 |

После возврата к старому входу пользователи, зарегистрированные только через Endemion ID, войти на сайт паролем не смогут: пароля на сайте у них нет (`password_hash = '!'`). Им поможет восстановление пароля сайта.
